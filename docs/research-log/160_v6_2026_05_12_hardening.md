## Audit 1 — All PowerShell launchers vs Rule 13

Doc 159 added Rule 13: "PowerShell launchers must use
`ErrorActionPreference=Continue`, not Stop." Audited every `.ps1` file
in `scripts/`:

| Script | Stop? | try/catch | python calls | Rule 13 risk? |
|---|---|---|---|---|
| daily_data_ingest.ps1 | No (Continue, post-fix) | 0 | 17 | FIXED (doc 159) |
| daily_paper_trade.ps1 | Yes | 4 | 6 | **No** — toggles to Continue around python |
| lottery_paper_trade.ps1 | Yes | 3 | 5 | **No** — uses `\| ForEach-Object` (no 2>&1) |
| fader_short_launcher.ps1 | Yes | 3 | 5 | **No** — same |
| run_backfill_daemon.ps1 | Yes | 1 | 2 | **No** — uses `*>>` file redirect |
| run_phase3.ps1 | Yes | 1 | 2 | **No** — no stderr capture |
| drift_cron.ps1 | Yes | 0 | 1 | Low — only 1 python call, no try/catch |
| watchdog_monitor.ps1 | Continue | 0 | 0 | OK |

**Refined Rule 13 understanding:** the actual trigger isn't `Stop`
itself — it's combining `Stop` with `2>&1 | ForEach-Object`. The
2>&1 redirect makes PowerShell wrap every Python stderr line as a
NativeCommandError ErrorRecord; `Stop` then terminates on the first
one (even INFO logs). My new launcher used both; the existing 4
launchers avoided 2>&1 (they use `| ForEach-Object` without the
redirect, or `*>>` file output) which is why they've been running
successfully for weeks.

The proper rule:
> **Avoid `2>&1 | ` redirect on native commands when
> `ErrorActionPreference = "Stop"`. Either toggle to "Continue" around
> the call, or write stderr to a file via `*>>` instead of pipeline.**

Implementation in my fixed daily_data_ingest.ps1: combined `Continue` +
no try/catch + explicit `$LASTEXITCODE` check. This is the
maximally-defensive pattern.

## Audit 2 — Watchdog restart policy

Watchdog (`watchdog_monitor.ps1`) is well-engineered:
- 3-tier staleness threshold (180s opening, 240s intraday, 900s off-hours)
- DateTimeOffset for proper UTC handling (D218 fix)
- Checks if stale-heartbeat PID is still running before counting as restart
- py-spy dump captured BEFORE killing (forensics)
- Circuit breaker (3 restarts/hour)
- Stop-Process -Force on the PID
- Relies on Task Scheduler's auto-restart-on-failure to bring bot back

**Bug found:** The Task Scheduler restart policy for
`MomentumX-PaperTrading` is `<Count>3</Count>` — should be `<Count>6</Count>`
per the `configure_paper_task_restart_policy.ps1` script's spec ("On
failure: retry every 5 minutes, max 6 retries").

Coverage envelope:
- Current Count=3: 3 retries × 5 min = **15 min** post-watchdog-kill window
- Spec Count=6: 6 retries × 5 min = **30 min** post-watchdog-kill window

**FILED for user action:** the configure script reports "Applied" but
`Set-ScheduledTask` doesn't persist `RestartCount` properly via the
PowerShell cmdlet (known Windows quirk). Direct XML re-registration
via `Register-ScheduledTask -Xml -Force` requires admin elevation.

User remediation:
```powershell
# Run from elevated PowerShell:
$xml = Export-ScheduledTask -TaskName 'MomentumX-PaperTrading'
$newXml = $xml -replace '<Count>3</Count>', '<Count>6</Count>'
Register-ScheduledTask -TaskName 'MomentumX-PaperTrading' -Xml $newXml -Force
```

(Current Count=3 is functional — gives 15 min restart coverage. Just
not the 30 min the system was intended to have. Not catastrophic.)

## Audit 3 — Pre-flight check thoroughness — FIXED

Pre-flight had 4 checks: Alpaca / Finnhub / Disk Space / Heartbeat
File. **NONE of them caught the D277 HALT_NEW_ENTRIES kill switch** —
which silently blocked 8 valid trades over 2 days.

**FIXED:** added `check_halt_switch` (5th check). Returns FAIL with
clear remediation message when the halt is on:

```
[FAIL] Halt Switch: HALT SWITCH IS ON -- bot will refuse ALL new OTO entries today.
       Source(s): MOMENTUM_HALT_NEW_ENTRIES env var = '1'.
       To lift: [Environment]::SetEnvironmentVariable('MOMENTUM_HALT_NEW_ENTRIES', $null, 'User')
       AND restart bot.
```

When the halt fires, pre-flight EXIT 1, daily_paper_trade.ps1 sees
the failure and aborts before launching the bot. Operator sees the
error in transcript at 04:30 ET, can lift the switch, and re-trigger
the task. Net win: visible in 1 minute instead of 4-12 hours.

**Tests added:** `tests/unit/test_preflight_halt_sentinel.py` — 5
unit tests covering:
- PASS when env unset
- FAIL when env=1
- FAIL on truthy variants (`1`, `true`, `TRUE`, `yes`, `YES`, `on`, `ON`)
- PASS on falsy variants (`""`, `0`, `false`, `FALSE`, `no`, `NO`, `off`, `OFF`)
- Sentinel registration in `main()` check list (guards against future
  refactor silently dropping it)

All 5 tests pass.
