## 1. D310 noise demotion (Pierce item #1 of "beyond Discord")

### The problem

Doc 171 wired `D310 *_NO_CALLBACK` as ERROR on every OTO buy fill. The callback won't be wired until L3 lands next week. Within a week the logs would be 90% `D310_NO_CALLBACK` and the operator's eye would stop parsing them — habituated to ignore the very signal they need at L3 ship time.

### The fix

- **WARNING by default** with concise message: `"dead callback (known; L2 backstops). Set MOMENTUM_D310_DIAG=1 for ERROR-level diagnostics."`
- **ERROR gated behind `MOMENTUM_D310_DIAG=1`** for explicit deep-dive sessions
- Both `CANCEL_NO_CALLBACK` and `RESUBMIT_NO_CALLBACK` paths updated

Operator runs normally with quiet WARNINGs. When L3 work starts, flip `MOMENTUM_D310_DIAG=1` for that session to capture the full ERROR diagnostic trail.

## 2. L2 heartbeat + watchdog (D313.v2)

### The problem

`HedgeIntegrityWatcher` is the single safety net for T2. If it crashes silently at startup (env typo, import error, race with main loop), the bot runs happily without it — and we revert to ghost-`TrailingStopManager` land. No alert.

### The fix

**Inside `HedgeIntegrityWatcher`** (`src/monitoring/hedge_integrity_watcher.py`):
- `_last_heartbeat_utc` instance var, set at the END of each successful `check_once()` tick
- `heartbeat_age_sec()` accessor — returns `None` if never ticked, else seconds since last tick
- `stats()` now includes `last_heartbeat_utc` for dashboards

**In `main.py`**, a NEW background task `_l2_watchdog_loop()`:
- Polls every 60s
- Asserts `_hedge_watcher_task` is not `.done()` (task didn't crash)
- Asserts `heartbeat_age_sec() < 90.0` (loop ticking on time)
- On stale: emits `D313.v2 L2_WATCHDOG` ERROR + sends `alert_critical` (CRITICAL severity → @here mention)
- Recovery logs once when heartbeat resumes

**The Pierce principle**: "watchers without watchers are unreliable by default." Tonight tonight L2 is no longer single-point-of-failure.

## 3. L2 correctness extension (D313.v2)

### The problem

L2's invariant was `qty != 0 → has_protective_order`. But what if the stop has wrong params:
- qty=50 on a position of 100 (covers half)
- side=buy on a long position (wrong direction → not protective)
- TIF=day instead of GTC (expires at 16:00 ET)
- stop_price=$0.01 on a $100 stock (functionally no protection)

L2 said `✅ hedged` because *a* stop existed.

### The fix

New `_check_stop_correctness()` method validates each matched protective order:

| Check | Pass criterion |
|---|---|
| Total covered qty | `sum(stop.qty) >= position.qty` |
| TIF | at least one stop has `time_in_force in (gtc, gtd)` |
| Stop price band (long) | `avg_entry × (1−0.30) ≤ stop ≤ last × (1−0.001)` |
| Stop price band (short) | `last × (1+0.001) ≤ stop ≤ avg_entry × (1+0.30)` |

Returns `None` if at least one matched order passes all checks. Returns a short string describing the specific issue otherwise. Wrong-params orders are treated as "unhedged" → emergency-stop path fires after the same 60s tolerance window.

New stats counter `incorrect_stops` surfaces in EOD report via D304 `d_codes_fired` as `D313v2-Nwrong_params`.

## 4. Durable alert spool — D314

### The problem

Discord webhook is a single point of failure. Rate-limit, connection drop, rotated URL = alert lost forever. The 90-day audit found 185 unhedge windows that *never appeared in any prior EOD* — the bot's "all healthy" report can be lying. Tonight we ensure even Discord outages don't lose CRITICAL pages.

### The fix

`src/monitoring/durable_alert_spool.py` (new ~230 LOC):

**`durable_post(webhook_url, payload, severity)`**:
1. Writes JSON record to `data/alerts/YYYY-MM-DD/<ts>_<seq>_<sev>.json` BEFORE any live POST
2. Attempts one live POST (5s timeout)
3. On 2xx: deletes the spool file
4. On failure: leaves the spool file for the retry loop
5. **Never raises** — alert-delivery failures must never block trading

**`run_retry_loop(shutdown_event)`** (background task in `main.py`):
- Every 60s walks `data/alerts/YYYY-MM-DD/*.json`
- Retries each undelivered record with a single live POST attempt per cycle
- Deletes on success
- After 50 cycles (CRITICAL) or 20 cycles (INFO/HIGH): leaves alone for stale-quarantine
- Records older than 24h move to `data/alerts/stale/` for operator review

**Integration**: `alerts._post` and `alerts._post_sync` now route through `durable_post` instead of raw httpx. All existing alert call sites (post_trade_open, alert_session_end_rich, etc.) automatically inherit durability.

## 5. Severity stratification + @here

### The problem

D313 EMERGENCY_STOP_FAILED is "fix before next session." D216 veto count is informational. Same Discord visual weight = operator misses the urgent one.

### The fix

`_post(webhook_url, payload, severity="INFO")` — new `severity` kwarg:
- **`CRITICAL`** → injects `@here` into payload content + gets 50-cycle retry budget (vs 20)
- **`HIGH` / `INFO`** → unchanged behavior (no mention, normal retry)

`alert_critical()` now passes `severity="CRITICAL"`. The L2 watchdog's emergency pages use `alert_critical` so any L2 failure pings the channel.

**Deferred to operator setup**: SMS / PagerDuty webhook URL. Once the operator drops a Twilio webhook into env, the spool's CRITICAL records can be teed to a second URL. ~10 LOC change when ready.

## 6. EOD mini-audit + cross-confirm

### The problem

The EOD report computes from in-memory bot state. The 90-day audit found 185 unhedge windows the EOD never flagged. Bot's "all healthy" can be wrong.

### The fix

Right before `alert_session_end_rich` fires, main.py pulls `_hedge_watcher.stats()` and injects 3 conditional D-codes into `d_codes_fired`:
- `D313-Nviolations` if `violations > 0`
- `D313-Nemerg_stops` if `emergency_stops > 0`
- `D313v2-Nwrong_params` if `incorrect_stops > 0`

Also emits a daily `D313 EOD STATS` log line so the operator can grep history.

If L2's stats say 0 across the board AND the bot's in-memory state agrees, the EOD is cross-confirmed. If they disagree, the operator sees both numbers in the Discord embed and knows one of the two systems is broken.
